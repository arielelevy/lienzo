# Revisión de cambios para Lienzo 0.4.0

Alcance autorizado: delta desde `v0.3.1`, centrado en los incidentes del canal Desktop, Codex CLI y las reglas de coordinación. La coordinadora revisa el árbol compartido; el Codex hijo implementa y verifica los arreglos. No es una auditoría completa de dependencias.

## Hallazgos durante la implementación

1. **Reactivación de reglas ajenas a la recuperación.** Llamar `retarget_rules(sid, sid)` para una regla estacionada seleccionaba también reglas apagadas manualmente y podía encenderlas por defecto. Se pidió limitar la recuperación del mismo id a reglas estacionadas y probar ambas coexistiendo.
2. **Cierre ordenado del servidor.** El cierre del bridge entrega `stop:true` a un poll en curso. El adaptador retornaba sin reconectar. Se pidió distinguir reinicio de desconexión explícita, mantener el consentimiento solo para el primero y no repetir trabajos inciertos.
3. **Tarjetas Claude sin UUID.** La recuperación llamaba al constructor de la ruta pública para tarjetas `pid-N` fuera del manejo de errores. Se pidió ignorar esas tarjetas sin abortar la limpieza de los enlaces válidos.
4. **El padre intermedio del adaptador ya terminó.** El adaptador persistente nace de un proceso Python de bootstrap que sale tras recibir `ready`. Reutilizar la validación por ancestros para el bootstrap de reconexión llega a ese padre muerto y rechaza al adaptador autorizado. La prueba con `verified_child` sustituido no cubría esta condición. Se pidió una validación ligada a la identidad exacta del adaptador autorizado y una prueba con el launcher terminado, sin confiar solo en archivos públicos ni en PID reciclables.
5. **Cambio parcial de URL al reconectar.** El adaptador asignaba la URL recibida antes de validarla y leer la credencial nueva. Un error conservaba esa URL para el próximo poll con la credencial anterior. Se pidió validar candidatos y aplicar URL/credencial juntos, con una prueba que rechace el destino inválido sin efectuar solicitudes hacia él.
6. **Ventana entre ready y publicación del consentimiento.** El lanzamiento opt-in podía anunciar conexión antes del barrido que publicaba su descriptor. La coordinadora agregó `before_first_poll`, fuera del Condition y serializado con `_lifecycle`. Publica antes de `registered`, exige ancestralidad OS cuando aún no hay dueño y cierra los handles incluso si falla. Tres regresiones cubren reinicio inmediato, error al persistir y cierre concurrente. El hijo hizo una segunda revisión de solo lectura sin encontrar bloqueos concretos.
7. **Aviso viejo después de una entrega posterior.** El aviso `sin_enviar` persistía con un recibo posterior ya confirmado. La reparación exige Codex vivo, ausencia de permiso pendiente, entrega exacta confirmada y timestamp estrictamente posterior. Invalida la caché de transcripción para reparar tarjetas sin crecimiento. La fase se toma del turno real; el recibo se conserva y no hay reenvío. Se probaron preguntas, permisos, fallo más nuevo, hash distinto y timestamps inválidos.
8. **Dos pruebas anteriores incompatibles con el contrato nuevo.** La global terminó con 2414 passed, 3 skipped y dos fallas. El caso de aislamiento de disparos tenía un origen inexistente, que ahora se archiva, y un reloj parcial sin `time()`: se le dio un origen vivo y se conservó el reloj real. El caso de carga esperaba borrar reglas huérfanas antes de reconciliar: ahora exige conservar las cuatro entradas, incluida la remota, hasta disponer del inventario. El archivo visible posterior ya tiene regresión específica. No se relajaron baselines ni se alteró el backend para satisfacer expectativas antiguas.
9. **Oráculo instantáneo de ancestralidad.** En una focal posterior pasaron 73 casos y el probe instantáneo de `verified_child` devolvió False una vez. No se midió su causa y no se declara falso positivo ni defecto corregido. La prueba se alineó con el contrato observable: el mismo adaptador debe reconectar en 10 s atravesando el gate OS real; el proceso extranjero sigue rechazado. El probe directo queda solo como diagnóstico si falla la reconexión, conservando el timeout original. No hay mocks de ancestralidad, reintentos del test ni cambio al validador de producción. El hijo revisó este ajuste de solo lectura y lo consideró válido. Se conservan el fallo original y las ejecuciones diagnósticas posteriores (37 y 15 casos aprobados).

Experimento aislado de la coordinadora: un proceso Python propio terminó con código 0 mientras se conservaba un handle. `proc_info` pudo consultar su PPID, pero `image_path` devolvió `None`. Conservar un handle no alcanza por sí solo para reutilizar el chequeo anterior de imagen de cada ancestro. Se exigió además demostrar que un descriptor público forjado no autoriza a otro proceso del mismo ejecutable/script.

Los primeros cinco hallazgos se corrigieron en el frente del hijo. La coordinadora resolvió el sexto y revisó la solución del séptimo implementada por el hijo. Las regresiones y la verificación real se registran debajo.

## Criterios de revisión

Conservar PID/FILETIME y la verificación del proceso dueño. No guardar tokens Claude en archivos, comandos ni logs. No convertir un rollout observado en autorización de cola CLI. No repetir mensajes inciertos. Conservar informes sin presentar una eliminación fallida como exitosa. No reactivar reglas apagadas por el usuario. Mostrar deshabilitación y archivo en la interfaz. Revisar caminos local y federado.
